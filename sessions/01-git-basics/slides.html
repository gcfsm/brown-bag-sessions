What breaks without version control

Five ways the folder of shame fails you

  • 01No real history — you see that a new file exists, never what changed between versions
  • 02No safe collaboration — two people editing at once means overwritten work, or a manual eyeball-merge of `_JOHN` and `_MARIA` copies
  • 03No accountability — who changed what, and why, is gone the moment the file is renamed
  • 04No safe experimentation — no cheap way to "try something," so people don't, or they duplicate the whole file "just in case"
  • 05Fragile "final" — "final" is just whoever renamed the file last

Where Git actually comes from

Git is rung three of a ladder

Each rung exists because the one before it had a specific, concrete problem — not because someone wanted a shinier tool.

Rung 1 — early 1990s

CVS: one server, one truth, no atoms

  • Commits tracked per file, not as one change — a 5-file commit was 5 mini-commits, and a failure partway left an inconsistent state
  • Revision numbers were per file (file.c at 1.7, file.h at 1.3) — no single number for "the project right now"
  • Directories barely versioned; renames usually just lost as delete+add

Rung 2 — early 2000s, built to fix CVS

SVN fixes the sloppiness — keeps the cage

CVSSVN
Commit atomicityPer-file — can end up half-committedAtomic — whole changeset, or nothing
Revision numbersPer-file, scatteredOne global number per repo
DirectoriesNot really versionedVersioned like everything else
Renames / movesUsually lostTracked as copy + delete

Still centralized, though — the core limitation carries over untouched: commit, history, and most branching all require the server, every time.

Rung 3 — 2005, still climbing

Git: every clone is the whole history

  • Every clone holds a full copy of the entire history — no server needed to commit or browse the past
  • Branching and merging are cheap and fast — branch → PR → merge is usable daily, not avoided
  • Commit and publish are two separate steps (previous slide) — the direct consequence of being distributed

Why this matters even more today

AI-assisted coding makes Git more important, not less

Faster

Claude can rewrite a whole file in seconds — far faster than the manual-naming era, or a solo human typing every line.

Larger

A single request might touch many files at once — one prompt, a dozen files changed.

Easier to skip review

Convenience makes it tempting to accept something you haven't actually read through.

Every guarantee, doing new work

Git's core guarantees, applied to Claude's output

History as safety net

If an AI change breaks something, see exactly what changed and revert — the same as any human change, just seconds instead of weeks late.

Branches as sandbox

Let Claude make sweeping changes on a branch, review the diff, throw it away if it's wrong — zero risk to your working code.

Diffs as review

Reading a diff is how you review AI-generated code responsibly — the same discipline as human-to-human review.

Commits as accountability

Even when Claude runs git commit itself, the name on it is yours — set once in your Git config. Accountability lives in identity and approval, not in who pressed enter.

The counterfactual

If we were still on SVN, none of this works

  • →Instant local commits — rapid-fire AI checkpoints either hammer the central server, or nobody bothers. The safety net disappears.
  • →Disposable branches — "let Claude go wild, throw it away if wrong" needs free, local branches. SVN branching was heavy enough that teams avoided it entirely.
  • →Parallel worktrees — running several Claude sessions on separate branches at once. Even one long-lived SVN branch was expensive; several in parallel was impractical.
  • →Instant revert — git revert is local and instant. Undoing in SVN means touching shared central history — slower, riskier, more hesitation.

Not a hypothetical

You're looking at the proof right now

This curriculum was built exactly this way — iterating with Claude turn by turn, adding a topic, committing, adding another, committing again, a dozen small changes in sequence.

Without Git, that process means re-sending whole files back and forth, manually tracking which version had which addition — the _FINAL_v2 chaos again, just at AI speed instead of human speed. What we just did to build this session would be largely impossible, or painfully slow, without version control.

Before the commands — one thing to remember

SVN commit = Git commit + push

GitSVN
Record locallygit commit — offline, instant, privatedoesn't exist as a separate step
Publish to shared historygit push — separate, explicit, onlinesvn commit — does both at once, always online

Ten commits on a plane, no signal — checkpoints, WIP, "let me try this" — then one push when you're ready. Every command on the next few slides leans on this split.

The daily loop

Local basics + branching

 terminal
git checkout -b fix-login-button  # create + switch

git status                        # what's changed, what's staged
git add .                         # stage everything
git commit -m "short, clear message"
git push -u origin fix-login-button  # first push, sets tracking

git log --oneline                 # compact history
git branch                        # list branches

Naming convention: short, descriptive, hyphenated — fix-login-button, add-student-search.

Push → PR → Review

Getting a change into main

git push -u origin branch→ Compare & pull request→ Title + description→ Reviewer decides

As author

  • Read your own diff first — catch typos yourself
  • Respond to every comment, even "done"

As reviewer

  • Read the diff, not just the description
  • Comment / Approve / Request changes
  • Be specific — "could null-error if X is empty" beats "looks off"

By hand, no shortcuts

Reading a conflict

Read both sides. Decide the correct final code — one side, the other, or a blend. Delete the three marker lines. git add the file, commit, push. Editor merge tools can help highlight — but you should be able to do this by eye.
