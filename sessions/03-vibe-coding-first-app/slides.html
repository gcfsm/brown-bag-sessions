The unit everything else is measured in

It all runs on tokens

  • 01A token is a chunk of text — roughly three quarters of a word. volunteer is one token; localStorage is three
  • 02Everything in the exchange counts — your prompt, every file Claude opens, every command's output, its thinking, its reply
  • 03Tokens are the meter — your context window, your plan limits, and your bill are all counted in the same unit

The next few slides are all the same idea from different angles: models, context, limits and effort are four ways of spending tokens.

How much Claude can hold at once

The context window is a desk, not a filing cabinet

  • 01What's on the desk — the conversation so far, your CLAUDE.md, every file read, every command's output
  • 02It isn't memory — every message re-sends the whole desk. A one-line question in a session you've had open all day still pays for the whole conversation
  • 03When it fills, it compacts — Claude Code summarizes the older history so the session survives. You lose detail, not the thread

What is vibe coding?

Driving development through prompts and fast iteration, not hand-typing every line — you describe what you want, Claude writes it, you run it and course-correct.

Good fit

  • Prototypes, first drafts, throwaway scripts
  • Small, well-scoped tools — "does it work" is easy to verify by running it
  • Anything mostly boilerplate, not a hard decision

Needs extra scrutiny

  • Anything touching real people's data
  • Security-sensitive logic — auth, permissions
  • Code you can't easily test by running it

What today is not

Vibe coding doesn't mean skipping review. It means more review.

More code, faster, means more to read, not less. Same bar as Sessions 1 and 2 — read the diff, require a passing check, get a second pair of eyes.

States the what and the constraints — not the how

A good prompt vs. a vague one

 prompt
Bad: "Make a function called checkRSVP that loops through
      an array and uses a for loop with an if statement to
      count yes values."

Good: "Build a single-file HTML page for a volunteer sign-up
      list. Plain HTML/JS, no framework, no build step — it
      needs to run by just opening the file. People can add
      their name to a shift; store it in localStorage so it
      survives a page refresh. Keep it to one file."

The bad prompt dictates how — defeats the point of having Claude write it. The good prompt states the what and the constraints, leaves the how to Claude.

Part of the skill is knowing what not to build

Don't hand-roll what already exists

Reinventing it

  • “Build an accessible dropdown from scratch”
  • Date pickers, modals, form-validation UI — hand-rolled
  • Subtly broken where a glance won't catch it: keyboard nav, focus traps, screen-reader labels

Reusing one

  • “Use a battle-tested component library”
  • Someone already hardened the edge cases you'd miss
  • Less code to review — and the accessibility comes with it

For React, the name to know is shadcn/ui — accessible components you copy straight in (hands-on in Session 4). The instinct starts now: before asking Claude to build a component, ask whether a good one already exists.

The call you make ten times a session

Redirect the thread, or start a fresh one?

Redirect

  • The approach is close, one decision is wrong
  • It still holds context you'd have to rebuild
  • Say why it's wrong, not just “fix it”

Start over

  • You've corrected the same thing twice
  • The thread is mostly wrong turns now — that's what gets re-sent every message
  • /clear, then one better prompt

Small, checkpointed asks beat one giant prompt — small diffs are the ones you can actually review, and cleanly revert when wrong.

Session 1's habit, at a different altitude

Ask what it did. Then check the part a summary can't prove.

  • 01Start with a summary — “what did you change, and why?” At volume this is how you keep up. It only works because something else is checking the code
  • 02Trust the check for what runs — an invented import or method dies the moment the code runs. Session 2's CI catches those without you reading a line
  • 03Read closely where being wrong is silent — right answer to the wrong question, real data touched, auth and permissions. Working code can still be the wrong code, and nothing red will tell you

A summary is only as good as your ability to judge it. Read diffs until you can — that is the skill the shortcut depends on.

The check that actually matters

Claude's confidence is not evidence.

“This should work” and “I ran it — here's the output” are different claims. You needn't run it yourself; have Claude run it and show you. Never accept a change nothing has executed.

Skills get better the way prompts do

When a skill misfires, fix the skill — not just this session

  • 01It didn't trigger — Claude ignored a skill that should have applied. The fix is almost always the description — it didn't match how you actually asked
  • 02It triggered but did the wrong thing — the instructions were vague or wrong. Same habit as slide 17: say why it was wrong, then edit the skill so the next run starts correct
  • 03Every fix compounds — it's banked for everyone who has the skill, from now on — unlike a one-off correction that dies when the session clears

Power tools come in Session 11 (skill-creator, /skill-doctor). Today the loop is enough: use it, watch it miss, tighten it.

The last step — it starts itself

A routine is the loop, running with nobody at the keyboard

  • 01What it is — a saved prompt plus the repos, environment and connectors it may touch. Runs on Anthropic's servers on a schedule or an event — your laptop can be shut
  • 02No permission prompts, and it acts as you — its commits, PRs and messages carry your name. So the lesson is scoping, not scheduling: give it only the repos and connectors it needs
  • 03A routine proposes; CI decides — it reads and suggests (a weekly triage, a security scan). Session 2's check is still the gate — never make a routine the thing that has to pass

We'll set a simple one up together — the deeper, tool-calling version is Session 11, once Claude has real tools to run.

Borrowed from Agile — the same loop, pointed at us

Treat the session like a sprint — close it with a retrospective

  • 01What went wrong? — where did we get stuck, lose time, or repeat a mistake — named plainly, without blame, so it can be fixed and not just endured
  • 02What should we keep doing? — the thing that worked and is easy to drop by accident — call it out so it survives into the next session on purpose
  • 03What should we stop doing? — the habit that cost more than it gave — retire it deliberately instead of carrying it forward out of momentum

It's slide 26's feedback loop aimed at the room, not a skill: a fix we agree on here is banked into the next session — the process improves the way the skills do, one honest correction at a time.
