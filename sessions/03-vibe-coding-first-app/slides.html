The unit everything else is measured in

It all runs on tokens

  • 01A token is a chunk of text — roughly three quarters of a word. volunteer is one token; localStorage is three
  • 02Everything in the exchange counts — your prompt, every file Claude opens, every command's output, its thinking, its reply
  • 03Tokens are the meter — your context window, your plan limits, and your bill are all counted in the same unit

The next few slides are all the same idea from different angles: models, context, limits and effort are four ways of spending tokens.

How much Claude can hold at once

The context window is a desk, not a filing cabinet

  • 01What's on the desk — the conversation so far, your CLAUDE.md, every file read, every command's output
  • 02It isn't memory — every message re-sends the whole desk. A one-line question in a session you've had open all day still pays for the whole conversation
  • 03When it fills, it compacts — Claude Code summarizes the older history so the session survives. You lose detail, not the thread

The habit that saves the most usage

Keep going, or start fresh?

Keep the session

  • Still the same piece of work
  • Claude already knows these files — that history is earning its cost
  • You'd only have to re-explain it

Run /clear

  • Moving to unrelated work
  • Old context is crowding out what you need now
  • You're talking around assumptions from an hour ago

/rename before you clear, and /resume finds it again later. Clearing is free — compacting isn't, because summarizing a conversation means reading all of it.

Coined by Andrej Karpathy, early 2025

Drive development through prompts, not hand-typed lines

Good fit

  • Prototypes, first drafts, throwaway scripts
  • Small, well-scoped tools — "does it work" is easy to verify by running it
  • Anything mostly boilerplate, not a hard decision

Needs extra scrutiny

  • Anything touching real people's data
  • Security-sensitive logic — auth, permissions
  • Code you can't easily test by running it

The one thing this is not

What changes today is volume, not standards.

Sessions 1 and 2's discipline — read the diff, require a passing check, get a second set of eyes — applies exactly the same to Claude's output as it does to your own. You'll review more code, faster, than you're used to. That's exactly why reviewing AI diffs gets its own section today.

For anything beyond a few lines: ask Claude to outline its plan before it writes code. One extra exchange, catches a misunderstanding while it's still a sentence, not a diff.

States the what and the constraints — not the how

A good prompt vs. a vague one

 prompt
Bad: "Make a function called checkRSVP that loops through
      an array and uses a for loop with an if statement to
      count yes values."

Good: "Build a single-file HTML page for a volunteer sign-up
      list. Plain HTML/JS, no framework, no build step — it
      needs to run by just opening the file. People can add
      their name to a shift; store it in localStorage so it
      survives a page refresh. Keep it to one file."

The bad prompt dictates how — defeats the point of having Claude write it. The good prompt states the what and the constraints, leaves the how to Claude.

Knowing which is faster is the actual skill

Redirect with a prompt, or just edit it yourself?

Redirect with a prompt

  • The approach is wrong
  • The issue will recur in multiple places
  • Give feedback on why, not just "fix it"

Just edit it yourself

  • A one-line fix you already know the answer to
  • Round-tripping through a prompt is slower than typing it

Small, checkpointed asks beat one giant prompt — smaller diffs are the ones you can actually review (next) and cleanly revert if wrong (Session 1's whole point).

Session 1's habit. Higher volume, same discipline.

What to actually check

  • 01Does it do what you asked — not "does it look plausible," does it match the prompt
  • 02Does it match existing patterns — a good diff follows the repo's conventions instead of inventing new ones next to them
  • 03Anything that looks hallucinated — an import, method, or config option that doesn't actually exist — often confident-sounding and syntactically perfect

The check that actually matters

Claude's confidence is not evidence.

"This should work" is not the same as "I ran it and it worked." The second one is what you're actually checking for — every time, the same way you would with your own code before opening a PR.

The loop closing — Claude typing, you still driving

Commit, push, let CI do its job

 terminal
git checkout -b add-volunteer-signup
# Claude writes it, you review it (previous slides)
git add .
git commit -m "Add volunteer sign-up list page"
git push -u origin add-volunteer-signup
# open PR -> watch lint-and-test run -> partner reviews

Small, frequent commits still apply — one commit containing "the whole feature" is exactly as hard to revert when Claude wrote it as when you did. The check doesn't know or care who wrote the diff — that's the entire point of Session 2 existing before this one.
