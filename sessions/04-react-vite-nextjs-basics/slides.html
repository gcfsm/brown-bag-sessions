If you extended the Session 3 tool

You've already felt the seam

More document.getElementById. More manual innerHTML string-building. More places where what's on screen quietly drifts from what your data actually says.

That wasn't a beginner mistake. That's how everyone did it, for a decade.

You didn't write bad code. You wrote 2006 — which makes it exactly the right place to start.

Era one — the server rendered everything

JavaScript was garnish

PHP, ASP, JSP, later Rails: the server built the entire page for every request. You clicked, the browser threw the whole page away, asked for a new one, and repainted. Every interaction was a full page reload. JavaScript validated a form, swapped an image on hover, opened a dropdown. It was not where the application lived.

And it was miserable to write, for a reason that has nothing to do with the language: every browser did something slightly different. IE6 against Firefox against Safari meant the same twenty lines needed three variations. Prototype.js (2005) and jQuery (2006) existed to make that stop — and got enormous for exactly that reason.

Then AJAX: update without reloading. So why are we reloading at all?

Era two — the Single Page Application

The browser takes over

Backbone.js, and then AngularJS (2010, Google). Load the page once and never reload it again. The server's job flips — it stops sending pages and starts sending data as JSON. The browser now owns rendering, routing, and state. Change the data, the screen updates itself; no getElementById anywhere.

And it created two new problems:

  • 1Nothing shows until a large bundle of JavaScript downloads and runs. On a slow phone: a blank screen.
  • 2Search engines got an empty page — the crawler received a shell; the content only existed after JS ran.

That second one isn't history. It's why a public site and an internal dashboard get different answers today.

Era three — Node.js

JavaScript escapes the browser

Ryan Dahl took V8 — Chrome's JavaScript engine — out of the browser and wrapped it in a runtime that could read files, listen on ports, and talk to databases. JavaScript was suddenly a server language, and "full-stack JavaScript developer" became a real job title.

npm (2010) became how code gets shared — and then how tooling gets built. Which answers a question beginners are right to ask: why does a front-end project need npm install at all, when the browser is what runs the code?

Because the tools are Node programs. Vite is. Next.js is. So is your CI job.

Era four — React, then Vue

The unit stops being the page. It becomes the component.

One self-contained piece of screen that owns its own patch. And with it, the shift that actually matters: you stop issuing instructions and start making a declaration.

Imperative — the old way

Find this element, change its text, hide that one.

Declarative — the new way

Describe what the screen should look like for a given state. The library works out what to change.

Your Session 3 drift becomes structurally hard — there's no second copy of the truth left to drift from.

The wheel comes back around

Server rendering returns — now with components

Put the last two eras together. JavaScript runs on a server (era 3). Components describe a UI (era 4). So run the components on the server, send finished HTML, and let it wake up as a live app once the JavaScript arrives.

Look closely at what that is: era one's answer, rebuilt with era four's tools — and it fixes exactly the two problems era two created. Something is on screen immediately, and a crawler gets real content. Next.js (2016) is that idea packaged. Vite (2020) is the SPA path, done fast.

And to be accurate about it: era one never actually ended. Server-rendered pages stayed the majority of the web the whole time. What came back around was the frontier — returning to something that never left, now carrying better tools.

Vite descends from era two. Next.js from era one. Neither is out of date — and that's why they deploy to two different Firebase products.

Four words — so your prompt lands, not so you can type them

The vocabulary you actually need

  • ·Component — one self-contained piece of the screen that owns its own patch: a volunteer card, a schedule row
  • ·Props — data handed down into it from whatever contains it. Read-only from the inside
  • ·State — data it owns itself and that changes. When it changes, that piece of screen updates
  • ·Route — a URL that renders a particular screen

If two components both need it, it can't live inside either one.

Not "simple vs. full" — that framing tells you nothing

In church terms

Which one, and when you decide

Vite → Hosting

Rostering dashboard, attendance tracker, admin panel. Volunteers log in; nobody needs to find it on Google. Login-gated content has no SEO story to lose — so era two's weakness costs you nothing, and this path is free at our scale.

Next.js → App Hosting

The idmc-gcfsm conference site, a ministry landing page. Public, and people find it by searching. Real distinct pages you want indexed.

Reversing this later isn't a rename — it's a rebuild plus a hosting migration.

Vite → Firebase Hosting

A folder of files on a CDN

  • ·Runs on Spark — no credit card. 10 GB storage, 10 GB/month transfer. Caps are hard, not billable: you get a wall, not a bill.
  • ·You trigger the deploy — CLI, or the GitHub Action from Session 2. Wired up properly in Session 7.
  • ·Nothing here can hold a secret. Everything shipped to the browser can be read by anyone with dev tools open.

Client-only is not backend-less.

It still talks to Firestore and Auth directly — and security rules decide who may read or write what. That's a real server-side permission check. It's just not one you wrote. (Sessions 5, 6, 9.)

Next.js → Firebase App Hosting

An application that keeps running

  • ·Git-triggered. Push to the live branch and it builds and rolls out. Merging a PR ships to production — which is exactly what Session 2's required checks are standing in front of.
  • ·Google Cloud, unhidden. Cloud Build builds a container, Cloud Run runs it, Cloud CDN caches it. When it breaks, those are the logs.
  • ·Requires Blaze. Real free allowances — ~10 GiB/mo traffic, 2M requests, 2,500 build minutes — but nothing stops at the line. Past it, it's a bill. (Session 16.)
  • ·apphosting.yaml — env vars, secrets, container size. Recognise the filename; you don't need to write one today.

What you're buying: the backend comes with it.

Three corrections, so nobody leaves with a rule that's too clean

What Next.js does not replace

"Next.js means no Cloud Functions" is false. It removes the endpoint you call — client asks, server answers. It does nothing about the kind that fires on its own: a Firestore document changed, a file was uploaded, or it's 2am and the nightly summary is due. Nobody calls those. There is no request. An API route only exists while someone is asking it something — so it can never be one, on any platform.

Blaze doesn't mean expensive. It means metered instead of capped. Spark says "you can't go past this line." Blaze says "past this line, it costs." For a church both are usually free — the real question is which failure you'd rather have: a site that switches off, or an invoice nobody was watching for.

"Google can't see a React app" is out of date — that was era two's problem, and Google fixed most of it. It now runs your JavaScript on a second pass, queued behind the first, sometimes days later. So the honest 2026 version isn't invisible, it's delayed and less certain: content behind a click or scroll still isn't indexed, and other crawlers — Bing, social link previews, AI crawlers — are further behind than Google. For a conference page with a date on it, "probably indexed, eventually" is still the wrong answer.

Plenty of real projects are still on Create React App — same era-two lineage as Vite, same static output for Hosting, just the previous generation of it. With the history, an unfamiliar tool is placeable rather than alarming: it's someone's answer from a particular year.

Asking for an API route in a project that deploys as a static site isn't a small ask — it's a hosting migration. Better to know that before you suggest it than after.

Call it, in pairs — one sentence of why each

Which path? And does it still need a function?

  • 1A volunteer rostering dashboard. Thirty leaders sign in; nobody else should ever see it.
  • 2The public conference site — schedule, speakers, venue. People find it by Googling it.
  • 3A public registration form that emails a confirmation, using a mail service's API key.
  • 4An internal attendance tracker that also posts a summary every Sunday at 9pm.

Then take scenario 1, write the prompt with the deploy target stated, let Claude scaffold it — and check the answer against your decision. Ship it: branch → review → PR → CI → merge. Don't deploy it today; that's Session 7.
