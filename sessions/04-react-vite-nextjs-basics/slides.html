Light on build-tool internals — on purpose

You don't need Vite's or Webpack's internals to use either well — the same way you didn't need V8 to write JavaScript. What you need is functional recognition: what command runs this, what file configures it, what should make you stop and ask.

Sessions 1 and 2 stay hand-typed. That boundary doesn't move.

The whole mental model, in one line

A component is a function that returns UI

 VolunteerCard.jsx
function VolunteerCard({ name, role }) {  // props: read-only
  const [signedUp, setSignedUp] = useState(false);  // state: owned here

  return (
    <div>
      <h3>{name} — {role}</h3>
      <button onClick={() => setSignedUp(true)}>
        {signedUp ? "You're in!" : "Sign up"}
      </button>
    </div>
  );
}

The rule of thumb

If a parent controls it, it's a prop. If it's private and changes, it's state.

name and role come from whoever renders the card — it never changes them itself. signedUp is local: clicking the button updates it, and only this card re-renders to match.

Different questions, not different tiers

Vite vs. Next.js — when to use which

ViteNext.js
What it isFast dev server + build toolA full framework — routing, server-side rendering (SSR), API routes built in
Use whenSimple client-only app, no SEO concernsReal multi-page routing, crawlable content, or a backend in the same project
Church exampleInternal admin tool, volunteer-only dashboardA public conference site — idmc-gcfsm's actual stack

Vite asks "run and bundle this fast." Next.js asks "build a whole multi-page site." A project needing routing, SEO, or a backend reaches for Next.js from the start.

Functional literacy, not mastery

Dev server, hot reload

 terminal
npm create vite@latest my-app -- --template react
cd my-app
npm install
npm run dev     # prints a localhost URL

Save a file — the browser updates without a full reload, state usually preserved. If it doesn't update, that's your signal something's actually wrong — ask Claude, don't puzzle through it alone.

Recognition, not mastery

If the project already uses something else

 package.json
"scripts": {
  "start": "craco start",  // CRA + Craco — "npm start"
  "build": "craco build"
}

Same job (dev server, hot reload, build), different tool, different command name. You don't need to know why a project chose Craco to work in it — notice the script name, use the right one.

Same idea, different amount of setup

Routing: URL changes, a different component renders

Vite

Not built in — add react-router, wire up routes yourself: this path renders that component.

Next.js

File-based — the folder structure is the URL structure. app/schedule/page.jsx → /schedule, automatically.

Same tool, now with real components

Rebuild the Session 3 tool as components

  • 1npm create vite@latest a fresh app, or extend one already started
  • 2Split it into at least two components — a list (props) and an item (its own local state)
  • 3Confirm hot reload actually updates the browser when you save
  • 4Ship it the same way as always — branch → Claude helps write it → you review → PR → CI → merge
