Before we touch Actions

Ten people branch Monday. Everyone merges Friday.

Each branch works fine, alone, all week. Friday, everyone merges into main at once. Now find out — together, for the first time — whether any of it actually fits.

What breaks without CI

Five ways "it worked on my branch" fails you

  • 01No shared truth until merge — every branch is only ever tested against its own, increasingly stale copy of main
  • 02Breaks are anonymous — ten changes land at once; which one broke the build is now a mystery to solve, not a fact you already know
  • 03Fixes get expensive — the bug is found days or weeks after it was written, not minutes — the author has moved on, context is gone
  • 04Merging gets scarier, not safer — teams merge less often "to avoid the mess," which only makes the eventual mess bigger
  • 05Review can't catch it — a human reading a diff cannot run the whole test suite in their head

The direct fix — coined late 1990s, Extreme Programming

Continuous Integration: merge early and often, verify every time

Without CI

  • Branches live for weeks
  • Verification happens by eye, at review time
  • A break surfaces on integration day — for everyone, at once

With CI

  • Merge the same day work starts
  • Every merge is built, linted, tested — automatically
  • A break surfaces in minutes, on the one change that caused it

This is the missing half of Session 1. Cheap merging (Git) plus automatic verification on every merge (CI) is what actually makes "branch → PR → merge, all day" safe at team scale — Git alone gives you the ability; CI is what makes doing so not reckless.

One step further — two doses today

If main always passes, shipping main can be automatic

Once every merge is verified, you can trust that main is always in a shippable state — so shipping stops being its own dreaded event and becomes no click at all. That's Continuous Delivery / Deployment.

facilitator: a real production pipeline→ you: build a free one yourself, later today

The other half of the Session 1 thread

A lint/test workflow doesn't care whether a human or Claude wrote the diff. It checks the result — every time, without getting tired, without skipping a step because the code "looked fine."

If Claude can propose a change and you can merge it in minutes, CI is what stops "fast" from becoming "fast and broken."

The vocabulary that matters

Workflow, trigger, job, step, action, runner

TermWhat it means
WorkflowThe whole .yml file — one automated process
Trigger (on:)The event that starts it — push, pull_request, a schedule, or manual
JobA group of steps on one runner. Multiple jobs run in parallel by default
StepOne command or one reusable action, run in order inside a job
ActionA packaged, reusable step someone else wrote — like an npm package, but for CI steps
RunnerThe disposable virtual machine your job actually executes on

checkout and setup-node aren't special — they're two of thousands of published actions on the GitHub Actions Marketplace. Deploy to Firebase, post to Slack, run a Lighthouse audit — there's very likely already an action for it.

One file: .github/workflows/ci.yml

Anatomy of a workflow

 .github/workflows/ci.yml
# shows up in the Actions tab
name: CI

on:                     # what triggers this
  push: { branches: [main] }
  pull_request: { branches: [main] }

jobs:                   # parallel by default
  lint-and-test:
    runs-on: ubuntu-latest
    steps:                 # run in order
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm install
      - run: npm run lint
      - run: npm test

Hands-on

From zero to a check on your PR

A human reviewer no longer has to manually run npm test locally to find out if a PR is broken — the PR tells you before anyone even opens it. Once it's run on main, drop ![CI](.../ci.yml/badge.svg) in your README — a visible payoff without opening the Actions tab.

The follow-through on Session 1's note

Making the check mandatory

  • □Repo → Settings → Branches → Add rule, pattern main
  • □Require a pull request before merging — no direct pushes to main, ever
  • □Require approvals — at least 1 reviewer, even on a small team
  • □Require status checks to pass — select lint-and-test (only listed once the workflow has run at least once)
  • □Require branches to be up to date before merging — the "merge often" half of Section 4, enforced automatically

The PR's Merge button itself goes gray until the check passes and a reviewer approves. Not discipline. Not a reminder. GitHub mechanically refuses the merge.

Everyone hits a red X eventually

Reading a failed Actions run

The workflow

  • Click the failed check on the PR (or the Actions tab)
  • Click into the failing job, then the failing step
  • Read from the bottom up — the error is the last few lines
  • Reproduce locally (npm install && npm run lint && npm test) before pushing a fix
  • Push — the same PR re-runs automatically

Common first-timer failures

  • Node version mismatch vs. node-version:
  • A file that works locally but was never committed
  • An env var / secret the runner doesn't have (Session 7)
  • A flaky test under CI's tighter resources

Automatic dependency PRs

Dependabot: security alerts vs. routine bumps

 .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
Security alertRoutine version bump
Why it openedA known CVE in a dependencyA newer version just exists
UrgencyReview and merge promptlyMerge when convenient, or batch
Safe defaultCI passes + no breaking changes in the changelog → merge it

CI verifies a merge. This ships it — no click.

Your first deploy, hands-on

 .github/workflows/deploy.yml
on: { push: { branches: [main] } }
permissions: { pages: write, id-token: write }
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with: { path: . }
      - uses: actions/deploy-pages@v4

Settings → Pages → Source: GitHub Actions. Merge this, and main deploys itself to <user>.github.io/<repo> — no Firebase account, no secrets (Session 7 is the real version).

Say it out loud: you didn't deploy anything. You merged a PR, and the deploy happened to you.
